# Stage 3–4：工程骨架、垂直切片与测试策略

本参考对应 [SKILL.md](../SKILL.md) 的 Stage 3「发射曳光弹骨架」与 Stage 4「垂直切片与测试」，
只定义产物质量；实现与验证按项目自己的流程进行。

## Stage 3：发射曳光弹骨架

Walking skeleton 不是空目录或成套接口，而是最薄、可运行、可持续长大的端到端实现。
它应尽早暴露真实接缝：构建、前后端通信、持久化、配置、CI、打包/部署。若项目最大风险位于
某个第三方或平台边界，骨架应穿过那个边界；否则“Hello World”只证明框架能启动。

### 最小链路

按项目形态选择一条：

- Web：页面动作 → API → 一条领域规则 → 存储 → 页面反馈；
- 桌面：窗口动作 → Tauri command/本地服务 → 文件或数据库 → UI 更新；
- Bot：测试事件 → handler → 规则 → 状态 → 测试响应；
- Pipeline：最小输入 → 一个真实处理步骤 → 可检查产物。

链路可以业务上很薄，但不能用 `assert true`、假部署或永久 mock 冒充接缝。外部付费/生产服务
不应进入自动化测试；用官方沙箱、协议级 fake 或契约测试，并单独验证真实环境集成。

**产物**：一条真实可观察的最薄行为、至少一个行为测试、绿色 CI，以及目标环境上的可重复
构建/打包或最小部署证据。README、runbook 等文档格式转 `skill://project-docs`。

### 仓库与标准动词

统一入口降低人和 Agent 的记忆负担，命令实现仍复用语言生态工具：

| 动词 | 语义 | 质量要求 |
|---|---|---|
| `make setup` | 安装/准备已声明依赖 | 幂等；新环境不依赖“我机器上正好有” |
| `make dev` | 启动本地开发 | 错误可见；停止后不留孤儿进程 |
| `make check` | 只读质量门 | 与 CI 调用同一入口；失败非零退出 |
| `make build` | 生成可交付产物 | 依赖版本锁定；产物可关联源码版本 |
| `make demo` | 可选的验收体验 | 只有产品确实需要交互 Demo 时提供 |

不必为无类型系统伪造 `typecheck`，也不必给一次性脚本建十几个空目标。标准动词是稳定接口，
不是空实现清单。项目专用操作可增加清楚命名的目标。

目录按业务责任和变更局部性组织；框架有成熟约定时优先遵循，不复制一套“通用分层模板”。
库 API 与脚手架版本用 Context7 MCP 的 `resolve-library-id`、`query-docs` 或官方文档核对。

### 配置与环境

Twelve-Factor 的可移植要点适合服务型应用，也可按项目形态取用：

- 依赖完整、明确声明并隔离，构建不依赖系统中偶然存在的工具；
- 会随部署变化的连接地址、凭据和主机名与代码分离，服务应用通常用环境变量；
- 环境变量彼此独立，而不是在代码里维护成套 `development/production` 分支；
- 开发、预发、生产尽量使用同类 backing service，减少“本地通过、线上不兼容”。

桌面应用的非秘密用户偏好不必强塞进环境变量；构建时公开配置也不等于运行时密钥。
`.env.example` 只列键名、格式和说明，不放真实凭据；必需配置应在启动边界明确报缺项。
详细配置、日志和健康检查归 `skill://backend-engineering`。

**工程基线足够好**：干净环境能按文档 setup/dev/check/build；CI 复用相同入口；
依赖与配置来源显式；一个真实链路已跨过主要技术接缝。

## Stage 4：垂直切片与测试

垂直切片是“一小段可观察能力”，不是技术层任务。它从一个用户/操作者输入穿过必要层次，
产生可验收结果，并能在合入后独立存在。

```text
好：用户能创建一条课程并在列表看到它
坏：先建完所有表 / 先写完全部 API / 先搭通用 Repository 层
```

### 切片边界

每片写清：

- 用户或操作者获得的结果；
- 一个正常例和最重要的失败例；
- 会变化的契约、状态和模块；
- 验证证据；
- 明确不触碰的相邻能力。

先做能降低最高不确定性、同时仍可端到端闭合的薄片。不要把“风险优先”误解为先建一套
未来基础设施；实验若不能成为可交付行为，应明确是 throwaway spike。

**产物**：生产行为，以及与风险相称的验证（新的业务规则或修过的缺陷通常值得一个行为测试），必要时同步更新 contract/spec/ADR/runbook。前端实现质量转
`skill://frontend-engineering`，API、数据和运行行为转 `skill://backend-engineering`，文档转
`skill://project-docs`。

**足够好**：切片可单独演示或由稳定接口观察；不存在等待未来层完成的半成品；所有受影响消费者
在同一变化中收敛。

## 测试组合：按风险，不按固定配额

SWEBOK 区分 unit、integration、system、acceptance 等测试层级，并列出边界值、状态转换、场景、
异常强制等技术。测试金字塔是启发式：多写快速、确定的小测试，较少写跨边界测试，最少写慢且
脆弱的端到端测试；具体形状由架构和风险决定，不追求固定百分比。

| 风险/问题 | 首选证据 | 重点 |
|---|---|---|
| 业务规则、计算、不变量 | 单元/属性测试 | 边界值、状态转换、拒绝路径 |
| 数据库、文件、队列、框架绑定 | 集成测试 | 真序列化、事务、约束、迁移 |
| 跨服务接口 | contract + 少量集成 | 消费者期待、兼容与错误语义 |
| 用户关键旅程 | 少量 system/E2E | 只保命脉，不重复所有组合 |
| 易用性、视觉、探索性风险 | 人工/可访问性/视觉验证 | 自动化不替代判断 |
| 性能、安全、恢复 | 专项验证 | 由明确威胁、SLO 或恢复目标触发 |

测试应断言公共、可观察行为。避免大量断言私有调用顺序、全靠 mock 自证、无断言 smoke test、
或为了覆盖率给无风险 glue code 补同义反复。每个重要变化都需要验证，但并非每个变化都值得
新增永久测试。

外部网络在测试中隔离：协议 fake、录制样本和本地测试容器应固定输入；不能用 sleep 猜异步完成。

### 何时增加哪一层

- 失败影响高且规则复杂：增加便宜的小测试覆盖组合；
- 接缝曾出错或实现差异重要：增加一条真实集成测试；
- 主旅程跨多个容器：保留一条 E2E，细节下沉到更快层；
- 测试比行为更难维护：检查是否测了实现细节，或模块边界本身不清楚。
