# 存量项目接入、复用与工程分寸

存量项目不重走一遍“新项目五阶段”。按 [SKILL.md](../SKILL.md) 的五阶段：
先做 Stage 1 的当前变化定界；只有契约/不可逆决定受影响才进 Stage 2；通常跳过 Stage 3；
从下一条 Stage 4 垂直切片开始改善，最后按 Stage 5 交付。

## Brownfield 第一目标：建立事实地图

接手时先观察，不因“不符合偏好”重构。SWEBOK 把 program comprehension、impact analysis、
reverse engineering、配置管理和持续交付列为维护核心主题；因此第一批产物应帮助安全改变系统。

按顺序建立最小事实：

1. **如何运行**：依赖、setup/dev/check/build/deploy 的真实命令；CI 实际执行什么；
2. **系统边界**：入口、进程/容器、数据存储、外部系统、主要调用方向；
3. **关键旅程**：一条用户或运维路径如何穿过代码、状态与外部依赖；
4. **契约与状态**：公开 API、文件格式、schema/migration、队列事件、配置键及消费者；
5. **运行事实**：当前部署方式、版本识别、监控、备份、已知事故与手工操作；
6. **风险热点**：频繁变化、故障历史、缺测试且后果高、只有一人理解的区域。

优先读仓库中的 README、manifest/lockfile、CI、入口、测试、migration、部署配置和近期真实变更；
文档与代码冲突时记录冲突，不默默选一边。需要回溯行为时先做有边界的调查，出现故障症状
先诊断再改（项目有 `investigate-question`、`debug-problem` 这类流程 skill 时用它们）。

**产物**：一页 system map（可用 C4 Context/Container）、经过实跑确认的命令表、契约/状态清单、
风险排序和“下一条最安全有价值切片”。项目文档模板转 `skill://project-docs`。

## 渐进接入，不做“清场式重构”

新标准从正在改的区域开始：

- 给既有命令包一层稳定入口，但不同时替换全部工具链；
- CI 复用这个入口；
- 为当前旅程补术语、契约和高价值测试，不全量补文档/覆盖率；
- 先加 characterization test 记录真实可观察行为，再改变不清楚的旧代码；
- 每个切片只偿还它实际触碰、且会降低当前风险的结构债；
- 发现不兼容历史接口时，先识别真实消费者和迁移义务。

不要一上来统一所有命名、接口、目录、测试或配置。这会把理解风险与修改风险叠加成一个不可审查的
大 diff。模块边界、API、数据与日志改造转 `skill://backend-engineering`；界面行为转
`skill://frontend-engineering`。

**接入足够好**：下一条真实变更能通过稳定命令构建/验证；其影响范围和消费者已知；
新代码遵循当前明确约定；历史问题不再阻挡安全交付。

## 按可逆性决定投入

投入不是按“项目看起来多专业”，而是按错误后果、发现速度、恢复成本和真实证据。

| 决定 | 典型例子 | 合理投入 |
|---|---|---|
| 局部、便宜、可快速撤回 | 私有函数结构、局部 UI 排版 | 做最简单可读实现，用快速反馈纠正 |
| 跨模块但可迁移 | 内部模块接口、依赖升级 | 查消费者、自动测试、明确迁移路径 |
| 外部契约或持久状态 | public API、文件格式、schema | 兼容/迁移计划、ADR、恢复演练 |
| 安全、权限、金钱、不可逆副作用 | authz、删除、付费调用、生产密钥 | 前置约束、最小权限、人工决策边界与审计证据 |

一个风险值得编码防御，通常至少满足：它发生过或是该技术边界的已知故障模式，并且后果足够高。
纯推测且后果低的分支不写；高后果但尚未证实的风险先记录并设计低成本验证，不用复杂框架伪装确定性。
失败可逆时允许明显失败并提供诊断；不要 catch 后返回假成功。

### 过度设计的可见信号

- 只有一个真实实现，却增加接口、插件、工厂或策略注册表；
- 没有观测到性能问题，却加入缓存、队列、分片或批处理；
- 没有第二个消费者，却先建“通用”平台层；
- 配置项从未有非默认值，或 feature flag 没有 owner/清理条件；
- 为“以后可能换库”包一层与业务无关、且仍泄漏原库语义的 adapter；
- 图、文档和检查项没有已知读者，也不会改变决定。

这不是禁止抽象。相同概念已重复变化、替换边界真实存在、或测试困难暴露耦合时，抽象是在降低整体复杂度。
目标是最小化系统整体复杂度，而非当前 patch 行数。

## 复用判断

按成本由低到高查：仓库已有实现 → 语言标准库 → 已安装依赖 → 成熟生态。找到候选后再比较：

- 是否覆盖当前必要行为和边界情况；
- 许可证、维护状态、安全记录、传递依赖与平台支持；
- 引入后是否比当前缺口更复杂；
- 能否用薄适配对齐领域词汇、错误和配置，而不复制整套能力；
- 退出/替换成本是否与该决定的风险相称。

协议、密码学、认证原语、时间/时区、金额、解析器、数据库 driver/迁移、重试与限流等边界复杂领域，
优先成熟实现；业务规则和很小、边界可穷举的 glue 保持项目内实现。具体库 API 必须用 Context7 MCP
的 `resolve-library-id`、`query-docs` 或对应版本官方文档核对；临时 Python 调研依赖用
`uv run --with <包>`，不要顺手写入项目 manifest。

**产物**：复用/新增依赖的简短决定；只有当它影响多个模块、非功能属性、公共接口或迁移成本高时
才升级为 ADR。

## 停止条件

当下一步只是“看起来更整齐”、不降低当前变化风险、不支持已知需求，也不改善真实运行问题时，停止。
DORA 也提醒：测量的目标是改善当前应用/服务，不是为了测量而建设精确但昂贵的集成。
