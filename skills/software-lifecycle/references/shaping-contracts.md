# Stage 1–2：需求塑形、领域语言与架构契约

本参考对应 [SKILL.md](../SKILL.md) 的 Stage 1「需求塑形与定界」和 Stage 2「契约与不可逆决策」。
文档格式由 `skill://project-docs` 负责；这里关注内容质量。
SWEBOK v4 把需求获取、分析、规格、验证、变更管理，以及架构的重要决策与视图分别列为核心活动；
这些活动是可迭代的，不意味着先写完一套大文档再编码。

## 0. 是否先做需求发现

先判断“这个需要是否真实”，再判断“怎么实现”。但对低成本自用工具、一次性脚本、已由需求方
明确拍板的任务，跳过正式发现是正常的：验证成本不应高于误判成本。

需要发现时，只收集会改变 go / no-go、范围或优先级的证据：

- **谁遇到什么现状**：真实任务、工单、日志、失败样本或直接观察；
- **目前如何解决**：手工流程和“不处理”也属于替代方案；
- **现状造成什么可观察后果**：时间、错误、机会、风险，不编造市场数字；
- **最不确定的假设**：需求、可行性、价值三类分开；
- **最低成本验证**：访谈记录、日志查询、纸面原型或可丢弃实验。

SWEBOK 将原型列为需求验证手段之一，而不是默认的生产实现。若实验代码故意牺牲质量，明确丢弃；
不要把它悄悄升级为骨架。

**产物**：一段带证据链接的判断：`做 / 不做 / 缩小后做`，以及尚未验证的假设。
小工具可以只在 issue 或工作契约中留几行，不强制新建报告。

## Stage 1：需求塑形与定界

### 先固定结果，不先固定方案

一份足够好的意图应回答：

1. 谁在什么场景使用；现在发生什么；使用后什么会改变；
2. 唯一主旅程的起点、关键动作、可观察终点；
3. 什么算成功，如何验收；
4. 明确不做什么，尤其是容易被 Agent “顺手支持”的相邻场景；
5. 部署、隐私、权限、兼容、数据等已知约束；
6. 哪些仍是假设，什么证据会推翻它们。

不要硬凑固定数量的非目标。列出实际存在的范围分叉即可；若没有分叉，简短说明也比虚构三条更好。
验收描述用具体输入、事件、状态和可观察输出，避免“高效、友好、智能”等不可判定形容词。
界面行为交给 `skill://frontend-engineering`，API 与失败语义交给 `skill://backend-engineering`。

**产物**：`docs/spec.md` 或等价工作契约，包含问题、用户与主旅程、验收例、非目标、约束和未决假设。
模板与写法见 `skill://project-docs`。

**足够好**：两个独立读者会对“完成/未完成”给出相同判断；技术方案不是问题陈述的一部分。

## 领域模型与词汇表

模型的用途是让需求、代码、接口和日志使用同一组概念，而不是展示 DDD 术语。
从主旅程提取名词、事件与规则：

| 内容 | 要回答的问题 | 例 |
|---|---|---|
| 术语 | 它是什么；容易与什么混淆 | `Order` 是已确认的购买记录，不是可变购物车 |
| 标识与关系 | 如何识别；生命周期由谁拥有 | `OrderId`；订单引用客户而不复制认证凭据 |
| 不变量 | 哪些状态永远不能出现 | 已支付金额不能为负；已取消订单不能发货 |
| 状态转换 | 什么事件允许从 A 到 B | `pending --pay--> paid`；其余组合拒绝 |
| 模块责任 | 哪些规则和数据一起变化 | 订单模块拥有订单状态；认证模块拥有凭据 |

小项目可能只需要半页术语和几个不变量。不要因为“做领域建模”就引入聚合根、仓储、事件总线。
当同一个词在两个业务场景含义不同，显式限定名称或模块边界；跨边界通过契约交流，
但是否拆进程是另一项架构决定。

**产物**：`docs/glossary.md` 或 spec 中的领域段，含术语、关键关系、不变量、必要状态机与责任边界。
模板归 `skill://project-docs`；存储约束和 API 表达归 `skill://backend-engineering`。

**足够好**：核心词在 spec、代码和契约中不漂移；每条不变量都能指向执行位置或测试策略。

## Stage 2：契约与不可逆决策

### 模块边界按责任与变化划分

边界应把同一概念和一起变化的规则放在一起，并让跨边界依赖显式。先用一个可部署单体内的模块
表达边界；只有部署独立性、扩缩容、隔离或组织约束提供具体收益时，才增加进程/服务。

### C4 视图做到“够沟通”

C4 官方把四级静态视图定义为 Context、Container、Component、Code：

- **System Context**：系统、使用者和直接外部系统；面向技术与非技术读者，先画这一张；
- **Container**：系统内可独立运行的应用和数据存储、责任、主要技术与通信；
- **Component**：只有某个容器内部边界确实需要解释时再画；
- **Code**：通常由代码和工具提供，除非某个局部设计难以从代码看懂。

图中每个元素写名称和责任，每条箭头写方向与意图；不要混用抽象层级。部署副本、负载均衡、
故障域属于 Deployment 视图，不要硬塞进 Container 图。

**产物**：至少一张 Context 图；非平凡系统再加 Container 图。图模板和存放位置见
`skill://project-docs`。

### 什么时候写 ADR

Michael Nygard 将 ADR 用于影响结构、非功能属性、依赖、接口或构建技术的架构重要决定。
据此，出现以下任一信号就写：

- 改变公共契约、数据所有权、部署拓扑、信任/权限边界；
- 选择会约束多个模块或未来迁移成本高的依赖、存储、消息或运行方式；
- 为满足质量属性作出不直观权衡，后来者很可能“优化”掉；
- 多个可行选项的后果不同，需要保留当时约束和取舍。

局部命名、容易撤销的库调用、显然遵循仓库既有约定的选择通常不写 ADR。
ADR 一项决定一份，记录 Context、Decision、Status、Consequences；决定被推翻时保留旧记录并标为
superseded，而不是改写历史。具体模板由 `skill://project-docs` 提供。

**产物**：`contracts/`、必要的 migration、C4 图和少量 ADR。公共 API、错误、鉴权、幂等、
数据迁移细节转 `skill://backend-engineering`；UI 契约转 `skill://frontend-engineering`。

**足够好**：每个跨边界契约都有已知消费者；每个高反悔成本决定写明后果和恢复/迁移方向；
可逆局部决定没有被文档仪式拖慢。
