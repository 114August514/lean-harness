# 文档地图：读者、职责与规模

## 1. 先问三件事

新建文档前写下：**谁会读、他要回答什么问题、什么变化会触发更新**。没有明确答案时，先在 README 放一个短节；不要创建无人维护的空壳。

推荐按信息的寿命分开：

- README 帮第一次接触项目的人定位并启动；
- spec 描述当前要达到的结果；
- ADR 保存重要决定发生时的上下文和后果；
- glossary 统一领域词义；
- runbook 支持带时间压力的实际操作；
- CHANGELOG 面向版本使用者说明值得注意的变化。

这是职责划分，不是固定目录法规。小工具可把多个短节留在 README；真实产品再拆文件，避免文档数量超过真实信息量。

## 2. README：项目入口

**读者：** 潜在使用者、新贡献者、未来的自己。

至少回答：

1. 项目解决什么问题，适合谁；
2. 当前状态与关键限制；
3. 最短安装/运行示例及预期结果；
4. 常用开发验证命令；
5. 详细 spec、用户文档、贡献与运维入口在哪里。

示例要可以复制，并展示成功信号。不要把完整 API、架构决策史和生产排障步骤塞进 README；入口越长，首次路径越难发现。技术文档优先清晰与一致，并服从项目自己的术语规范，这是 [Google developer documentation style guide](https://developers.google.com/style) 的参考层级原则。

## 3. spec：要得到什么结果

**读者：** 提需求者、实现者、评审者、验收者。

spec 应记录问题、用户/场景、范围与非目标、可观察的验收标准、约束和未决问题。它回答“**做成什么样**”，不替 ADR 回答“为什么选择某个架构”。

好的验收项包含具体触发、可观察结果和重要失败路径：

```text
当用户导入不支持的文件类型时，系统拒绝导入，说明支持的类型，且不创建部分记录。
```

而“体验友好”“性能良好”无法直接验收，应改成场景与边界。

Lean Harness 已有 `templates/project-skeleton/docs/spec.md`，它还承担 shaping、主旅程、非目标、曳光弹、REQ-ID 和垂直切片跟踪。项目已经采用它时继续维护该文件；本 skill 的通用模板只用于没有既有格式的仓库。`docs/walkthrough.md` 是交付状态与人工验收入口，不是长期需求或设计决定的事实源。

## 4. ADR：为什么这样设计

**读者：** 当前评审者、未来维护者和后来接手者。

ADR 只记录一个重要决定，细则见 [decisions-and-releases.md](decisions-and-releases.md)。判断边界：

- “系统必须让离线用户继续编辑”是需求/约束，放 spec；
- “选择本地 SQLite 并采用同步队列满足离线编辑”是决定，放 ADR；
- “执行 `app migrate` 后观察哪个指标”是操作，放 runbook。

## 5. glossary：这个词到底指什么

**读者：** 产品、设计、开发、数据和支持人员。

只收录在本领域中可能歧义、会影响行为或跨边界交换的词。每条给出首选术语、精确定义、必要时列出“不是/别名/代码标识”。不要把通用技术词全部抄成词典。

当同一概念在 UI、API、数据库和代码中出现时，链接 glossary，并让名字尽量一致；翻译或历史兼容名要明确映射，不要悄悄创造近义词。

## 6. runbook：现在该怎样操作

**读者：** 发布者、值班者、事故处理者，以及不熟悉系统但必须恢复服务的人。

每个操作写清：前置条件、权限、可复制命令、成功信号、失败时停止条件、回滚/恢复路径。凭据只写“从哪里安全取得”，不把秘密值放入仓库。

按任务组织，例如“部署”“回滚”“恢复备份”“处理队列积压”，不要按组件堆背景介绍。runbook 是 how-to；架构原理应链接 explanation/ADR，参数表应链接 reference。演练后更新实际命令和耗时，而不是让事故现场验证文档是否正确。

## 7. 用户文档：按 Diátaxis 分开需求

[Diátaxis](https://diataxis.fr/start-here/) 把用户需求分成四类：

| 类型 | 用户处境 | 写法 | 例子 |
|---|---|---|---|
| Tutorial | 正在学习 | 安全、连续、由作者带领完成一次体验 | “第一次创建并运行机器人” |
| How-to | 已会基础，正在完成真实任务 | 以目标为标题，给可执行步骤 | “怎样迁移到新数据库” |
| Reference | 工作中查准确事实 | 中性、完整，结构贴近被描述对象 | API 参数、配置项、错误码 |
| Explanation | 学习中理解背景和联系 | 解释原因、取舍和概念关系 | “为何采用事件驱动同步” |

不要在 tutorial 中插入大段原理，也不要在 reference 中夹带某个任务的步骤；[Diataxis 指出](https://diataxis.fr/start-here/#the-diataxis-map)，混淆边界是大量文档问题的来源。规模小时可以在同一站点或文件内分节，但标题仍应让读者知道自己处于哪类内容。

## 8. 维护而不是囤积

- 改行为时，同一变化内更新其权威文档；失效内容应删除或改正，不保留“另一个版本的真相”。
- 链接权威内容而不是复制。必须重复时，明确哪个是生成源或怎样机械校验一致性。
- 文档示例也是接口使用者会复制的代码；涉及第三方库版本时，用 Context7 查询当前 API。
- Google 的风格指南建议使用主动语态、明确条件、描述性链接和无歧义日期，详见 [Highlights](https://developers.google.com/style/highlights)。中文正文不必照搬英语标点规则，但应保持直接、具体、一致。
