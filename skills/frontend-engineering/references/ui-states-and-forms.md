# 界面状态与表单

## 异步界面的状态模型

NN/g 的第一条启发式要求界面及时让用户知道系统状态。对每个取数边界，先写出状态表，再写 happy path：

| 状态 | 用户需要知道 | 常见呈现 |
|---|---|---|
| `loading` | 正在做什么，是否仍可操作 | 与内容形状接近的 skeleton、进度或简短状态文字 |
| `empty` | 是从未有数据，还是筛选无结果；下一步是什么 | 区分“首次为空”和“过滤为空”，提供相关主行动 |
| `error` | 什么没完成、哪些内容仍有效、如何恢复 | 就近错误、重试；不要抹掉仍可用数据 |
| `success` | 结果是什么，动作是否完成 | 内容与必要的成功反馈 |
| `partial` | 哪部分可用、哪部分失败或仍在刷新 | 保留成功部分，标出缺失范围并提供局部重试 |

`partial` 不是每页都要有；聚合多个独立请求、分页追加失败、后台刷新失败但旧缓存仍可读时才需要。
“有缓存数据 + 正在刷新”也不同于首次 loading：通常保留内容并给非阻塞刷新提示，而不是退回整页 skeleton。

不要用多个不受约束的布尔值表达互斥状态。React 的状态结构指南建议消除矛盾状态；discriminated union 或查询库提供的状态机更容易穷举渲染。

### 状态反馈与辅助技术

WCAG 2.2 的状态消息条款要求：不移动焦点的成功、等待、进度、结果或错误提示，应能由辅助技术通过 role 或属性识别。普通进度/成功可用适当的 `status` live region；紧急错误才考虑 `alert`，避免页面对读屏过度“话痨”。

## 空、错与部分成功

- 空状态不能只是空白；说明“为什么空”并给与原因匹配的行动，例如清除筛选或创建第一项。
- 错误不是异常堆栈。展示用户语境中的问题与恢复动作；机器分支依据稳定错误码，文案规则见 [交互文案](ux-writing.md)。
- 若整页失败，保留导航和上下文；若一个 panel 失败，只替换该 panel。
- 重试应重放幂等的读取或由后端保证幂等的命令；相关契约见 [`backend-engineering`](skill://backend-engineering)。
- 部分成功必须明确边界，例如“10 个文件已上传，2 个失败”，不能只弹“上传完成”。

## 表单设计

### 字段与说明

WCAG 3.3.2 要求接受输入时提供 label 或说明；格式特殊时应在输入前/旁给出规则或示例。可见 label 与程序化名称解决不同问题，不能只用 placeholder 代替：placeholder 会随输入消失，也可能缺乏足够上下文。

优先原生控件与正确的 `type`、`name`、`autocomplete`。一组 radio/checkbox 用 `fieldset` + `legend` 表达组名。字段帮助与错误通过项目采用的可访问关联方式连到控件。

### 校验时机与职责

- **输入时**：适合不会打断输入的格式化、计数和肯定反馈；不要用户刚键入首字符就持续报错。
- **失焦时**：适合字段已具备可判定值后的局部检查。
- **提交时**：运行完整客户端规则，列出并定位所有已知错误。
- **服务端返回时**：处理唯一性、权限、并发冲突等客户端无法可信决定的规则。

客户端校验减少往返并改善体验，不是安全边界；服务端仍验证所有不可信输入。

WCAG 3.3.1 要求自动发现的输入错误用文字识别错误字段并描述问题；颜色、图标可辅助但不能是唯一表达。长表单可同时给顶部摘要和字段旁错误，并把焦点移动到摘要或第一个错误位置，前提是行为可预测。

```text
差：红色边框 + “无效”
好：邮箱地址 — “请输入 name@example.com 格式的邮箱地址”
```

### 提交生命周期

1. 保存用户输入，不因一次失败清空；
2. 提交期间让当前动作状态可见，并防止重复触发；
3. 成功后清楚说明结果和下一步；
4. 失败时区分字段错误、业务冲突、权限/认证、网络不可达和未知错误；
5. 是否允许重试取决于命令幂等契约，不由前端猜测。

“禁用提交按钮直到表单完美”可能让用户难以发现缺什么；项目可以在规则明确时禁用，但必须同时让原因可见。提交中禁用是避免本地重复操作的体验保护，不能替代后端幂等。

## 对话框与破坏性动作

Apple HIG 建议 alert 只用于需要立即注意的关键信息，并避免为可撤销的常见操作反复打断；不可撤销且少见的破坏性操作才适合确认。按钮标题使用动作结果（如“删除”）而非含混的“确定”，并提供安全退出。具体文案见 [交互文案](ux-writing.md)。

## 检查问题

- 首次加载、后台刷新、空数据、筛选无结果、失败和部分失败是否可区分？
- 用户失败后是否保留已输入内容和仍有效的数据？
- 每个输入是否有可见且程序关联的 label；错误是否用文字指向具体字段？
- 键盘和读屏是否能获知 pending、错误与成功？
- 重试与重复提交策略是否来自后端契约？
