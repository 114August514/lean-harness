# 交互文案与反馈

交互文案帮助用户理解系统状态、作出选择并从错误中恢复。它不是后端异常的直译，
也不是用语气掩盖产品行为。视觉语气与品牌表达属于
[`frontend-design`](skill://frontend-design)；错误码与错误信封由
[`backend-engineering`](skill://backend-engineering) 定义。

## 场景索引

| 场景 | 重点 |
|---|---|
| 错误与异常 | 说明具体问题、受影响动作和恢复办法 |
| 破坏性确认 | 只在确需中断时使用，按钮写动作结果 |
| Toast / Snackbar | 短暂、非阻塞的进度或结果，不承载必须阅读的关键信息 |
| 空状态 | 区分首次为空与筛选无结果，给相应下一步 |
| 表单 | 可见 label、预先说明格式、文字错误关联字段 |
| 术语与语气 | 与用户语言、平台惯例和产品词汇表一致 |

## 错误：让用户能恢复

NN/g 的错误恢复启发式要求：用普通语言准确指出问题，并建设性地给出解决办法；
WCAG 3.3.1 进一步要求，自动识别的输入错误必须用文字指出出错项目并描述问题。

一个实用结构是：

```text
[没完成的动作或当前状态] + [用户能理解的原因（已知时）] + [下一步]
```

不要编造原因。系统只知道“请求超时”时，不要断言“你的网络断开”；可以写：

```text
差：出错了 / 500 / NullPointerException
好：订单未保存。请求超时，请重试；再次失败可提供请求编号 RQ-123 给支持人员。
```

机器逻辑按稳定 `error.code` 分支，再映射本地化文案；不要匹配可修改、可翻译的
`message` 字符串。未知错误保留诚实的兜底和诊断关联 ID，不把堆栈、SQL 或内部对象
直接给用户。

错误提示可以放字段旁、摘要、alert 或 dialog；WCAG 不规定唯一位置。选择位置时让错误
靠近受影响任务，并确保读屏能获知。颜色和图标可辅助，但不能替代文字。

## 确认框：少打断，写清结果

Apple HIG 建议 alert 只承载需要立即注意的关键信息；仅提供信息时优先在上下文中展示。
常见且可撤销的删除通常不必确认；少见、不可撤销且可能造成数据损失的动作才值得中断。

文案结构：

```text
标题：永久删除“年度预算”？
说明：删除后无法恢复，其中 3 个共享链接也会失效。
按钮：取消 | 删除
```

- 标题直接、具体，避免“错误”“警告”这类没有信息的标题；
- 按钮写结果动词，如“删除”“覆盖”“允许”，不用含混的“是/否”或“确定”；
- 破坏性动作提供清晰的安全退出；
- 正文只补充标题没有说明的后果，不重复标题。

Microsoft 的 dialog 指南同样建议：首行明确问题或目标、按钮使用与问题对应的具体回答，
并至少提供一个安全、非破坏性动作；字段校验等局部错误应留在页面上下文，不滥用 dialog。
按钮排列和默认焦点遵循目标平台惯例，不跨平台硬套一种顺序。

## Toast / Snackbar 与状态消息

Material Design 3 将 snackbar 描述为屏幕底部的简短应用进程更新，可自动消失，也可保留到
用户采取动作。适合“已保存”“链接已复制”这类轻量反馈；不适合需要阅读、比较或决定的
阻断错误。

WCAG 4.1.3 要求：不取得焦点的成功、结果、等待、进度或错误状态，能被辅助技术通过 role
或属性识别。普通成功/进度使用非打断式状态；紧急错误才使用更强提醒。不要让每次细小变化
都被读屏宣告。

```text
好：已保存
好：已移至废纸篓　撤销
差：用会自动消失的 Toast 展示“付款失败，请重新选择付款方式”且没有其他持久入口
```

不设脱离上下文的固定“字数上限”或统一停留秒数；长度、语言、读屏和用户所需阅读时间都会
影响设计。关键信息应持久存在或由用户明确关闭。

## 空状态

先区分原因，再写行动：

| 原因 | 文案方向 | 行动 |
|---|---|---|
| 从未创建 | 说明这里将出现什么 | 创建第一项 |
| 筛选无结果 | 说明未找到匹配项 | 修改或清除筛选 |
| 权限不可见 | 说明当前账号看不到什么 | 申请权限或切换账号 |
| 加载失败 | 这是 error，不是假装 empty | 重试或查看可用缓存 |

```text
标题：没有匹配的成员
说明：请尝试其他姓名或工号。
按钮：清除筛选
```

空状态行动不是强制“总要有一个 CTA”；如果用户没有可执行动作，就诚实说明状态，不放无效按钮。

## 表单文案

WCAG 3.3.2 要求接受用户输入时提供 label 或说明；特殊格式可提前给规则或示例。
可见 label 不能只靠 placeholder 替代，因为用户输入后 placeholder 会消失。

- 字段名使用用户概念，不使用数据库列名；
- 必填、格式、单位和限制在输入前或旁边说明，不等失败后才揭示；
- 错误文字指出字段和可修正内容，例如“邮箱地址：请输入 `name@example.com` 格式”；
- 不责怪用户；写“日期不能晚于今天”，不写“你输入了错误日期”；
- 服务端冲突（名称已存在、版本过期）与格式错误使用不同恢复动作；
- 提交成功反馈描述真实结果，不在尚未持久化时写“已保存”。

校验时机和状态管理见 [界面状态与表单](ui-states-and-forms.md)。

## 术语与语气

NN/g 建议界面说用户熟悉的语言，遵循现实世界、平台和行业惯例，并在产品内部保持一致。
维护项目词汇表，记录有真实语义差异的词，而不是宣布一套适用于所有产品的“唯一正确词典”：

| 词 | 本产品中的语义示例 |
|---|---|
| 保存 | 保留草稿或配置，可继续编辑 |
| 提交 | 发送进入后续处理流程 |
| 删除 | 数据被销毁或进入删除流程 |
| 移除 | 从当前集合解除，不销毁原对象 |

语气保持直接、中性、可接近。错误和数据损失场景避免玩笑、卖萌或庆祝；成功反馈简洁，不抢走
用户注意力。Apple HIG 对 alert 也建议直接、中性，避免含糊、指责或淡化严重性。

## 自查

- 错误是否准确说明没完成什么，并给真实可执行的下一步？
- 是否按错误码映射，而非解析后端 message？
- dialog 是否确有中断必要，按钮是否写动作结果并提供安全退出？
- 短暂反馈消失后，关键结果或恢复入口是否仍可获得？
- 输入是否有可见 label，规则是否在需要前出现，错误是否关联具体字段？
- 文案是否使用用户术语并与产品其他位置一致？
- 动态状态是否能被辅助技术获知，而没有制造过度播报？
