# Systematic Diagnosis（D2）

D2 用于：多个合理假设并存、难复现或间歇发生、涉及竞态 / 性能 / 环境 /
跨系统状态，或简单修复已经失败的问题。

本文件是 `debug-problem` 的按需参考，只在诊断深度判定为 D2 时读取。

---

## 路径

```text
建立反馈循环
→ 提高复现率
→ 缩小场景
→ 形成可证伪假设
→ 定向观测
→ 确认根因
→ 修复
→ 验证原始症状
→ 清理临时调试产物
```

### 1. 建立反馈循环

先让自己能反复、低成本地观察到问题：一个可重跑的复现脚本、
一条能触发症状的请求序列、或一个放大故障频率的测试。
没有反馈循环时，后续每一步都在碰运气——优先把它建出来，
哪怕它本身需要一次小型调查。

### 2. 提高复现率

间歇性问题先攻复现率：放大并发、缩小数据规模、注入延迟、
加快时钟或重试频率。目标是把"偶尔发生"变成"按需触发"，
或在可控运行次数内以已知概率触发。

### 3. 缩小场景

二分配置、数据、代码路径和环境变量，找到仍触发症状的最小场景。
每砍掉一个变量，假设空间就缩小一半。记录每一步排除了什么。

### 4. 形成可证伪假设

假设必须能被某个具体观测推翻。"可能是并发问题"不是假设；
"两个 goroutine 在无锁情况下交替写该字段，导致后写覆盖先写"是假设。
为每个假设写下：什么观测能证实它、什么观测能证伪它。

### 5. 定向观测

只收集能区分当前假设的观测：针对性日志、断点、metrics、trace。
不要默认铺开全量日志——观测过多会淹没信号，也可能改变被观测
系统的行为（尤其是竞态）。

### 6. 确认根因

根因确认的标准：能解释全部已观察到的现象，且其证伪条件未被触发。
只解释部分现象的"根因"通常是中间原因——继续向下追问。

### 7. 修复

针对根因修复。修复方案应考虑：是否消除整个故障类别，而不只是
当前触发的那一条路径。

### 8. 验证原始症状

用最初的复现方式验证原始症状消失。D2 问题还应增加针对故障类别的
验证（例如对并发路径的重复压测），但不默认新增永久测试——是否保留
测试按 `policy/working-contract.md` 的"测试与验证"判断。

### 9. 清理临时调试产物

删除或撤下：临时日志、debug 开关、复现脚本、注入的延迟、
观测用 instrumentation。只有确有长期价值的（如针对真实回归的测试）
才按正式交付标准保留。

---

## 停止条件

出现以下情况时，停止继续系统化诊断，回到 `debug-problem` 的交棒逻辑：

- 根因确认且修复验证通过：正常交棒；
- 复现率经努力仍不足、观测手段耗尽：记录已排除假设、剩余观测方案和
  复现条件，交 `finish-work` 判断；
- 诊断揭示问题源于结构性缺陷而非局部错误：停止局部修复，把结构判断
  带回主 Agent，可能转为 `implement-change` 工作。
