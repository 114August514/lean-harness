# Incident Mode

Incident Mode 与诊断深度 D0–D2 正交：它不改变"如何诊断"，只改变
"先做什么、谁有权做什么"。

本文件是 `debug-problem` 的按需参考，只在出现以下影响时读取：

- 生产或共享环境；
- 必须保留的数据或状态；
- 安全、隐私；
- 资金；
- 重大可用性。

---

## 顺序

```text
先控制影响
→ 保存证据
→ 确认授权边界
→ 使用合适诊断深度
→ 安全恢复
→ 记录残余风险
```

### 1. 先控制影响

第一目标是止损，不是找根因。能减轻影响的手段：回滚、降级、
限流、隔离故障面、切流量。所有控制动作都在授权边界内进行（见第 3 步）；
未获授权时，准备好建议方案并立即请求决定，同时继续做不需要授权的
观测和证据保存。

### 2. 保存证据

在系统被改动之前保存现场：日志、指标快照、报错原文、触发路径、
最近变更清单、相关数据状态。回滚或重启之后这些证据常常永久消失，
而诊断还依赖它们。

### 3. 确认授权边界

Incident Mode 不授权 Agent 自主执行未获许可的：

- 生产写操作；
- 数据恢复或数据修改；
- 发布、回滚、重启；
- 对外通知。

这些动作以 `policy/decision-boundaries.md` 的"发布与外部操作"和
"未明确授权时禁止执行"为准。已获明确授权的动作可以执行，但应记录：
谁授权、授权范围、执行了什么。

### 4. 使用合适诊断深度

Incident 不等于 D2。影响面大但根因明确的问题仍然是 D0——
例如生产上一个已知的配置错误，控制影响后直接修复。
按 `debug-problem` 的正常规则选择 D0 / D1 / D2。

### 5. 安全恢复

恢复动作要可验证：恢复后确认原始症状消失、影响面收敛、
没有引入新的异常。分步恢复时每一步都验证，不一次性堆叠多个变更。

### 6. 记录残余风险

交付前明确记录：

```text
已排除的风险
仍存在但未处理的风险
需要后续跟进的事项（由谁、何时）
```

Incident 的完成不等于"系统恢复了"，而是"影响受控、证据保留、
残余风险有归属"。
