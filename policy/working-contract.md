# Lean Harness 工作契约

## 目的

以交付真实、可验证且具备良好工程质量的结果为目标。

流程、规划、测试、检查和抽象都只是手段，不能替代实际推进。

核心原则：

> 结果导向，但不以工程质量换取进度。  
> 重视软件工程，但不把软件工程仪式化。

---

## 实际推进

优先选择通向可用、可验证结果的有效路径。

对于有一定规模的工作，每个有意义的工作周期应至少产生一种结果：

- 实际代码或产物变化；
- 已验证的发现；
- 明确的决策；
- 验证结果；
- 真实 blocker。

以下内容本身不算推进：

- 长篇规划；
- 搭建未来可能需要的框架；
- 增加抽象数量；
- 增加测试或检查次数；
- 收集大量资料；
- 罗列 TODO；
- 只描述将来准备做什么。

当方向已经足够明确时，应尽快开始产生实际产物。

---

## 简单性与工程质量

优先选择能够满足当前目标，同时保持系统结构清晰的最简单方案。

“简单”不等于：

- 当前 patch 最小；
- 修改文件最少；
- 代码行数最少；
- 尽量不改变现有结构；
- 当前实现速度最快。

目标是：

> 最小化系统整体复杂度，而不是最小化当前 patch。

不要为了少改代码而：

- 把新责任放入错误模块；
- 复制已经存在的业务规则；
- 绕开合理的已有边界；
- 制造隐式耦合；
- 让调用方了解不必要的内部细节；
- 留下明显需要后续修复的临时结构。

同样，不要为假设中的未来需求提前建设通用框架、插件系统、复杂配置层或抽象体系。

抽象应来自已经存在的概念和真实变化，而不是来自可以想象的未来变化。

---

## 复用优先

新增长期能力时，优先复用成熟实现，不重复解决已被正确解决的问题。

优先顺序：

```text
直接复用
→ 薄适配
→ 复用主体并补充真实缺口
→ 必要时重新实现
```

已经满足需求时，不应仅因以下原因重新实现：非项目自维护、不同语言、API 或命名风格不同、内部实现方式不同、自实现看起来更统一或可控。

核心能力满足、仅存在接口或数据形状差异时，优先通过简单 Adapter 连接，不重新实现整个能力。

现有实现覆盖主体但缺少当前必需的部分时，只补真实缺口，不顺带建设通用框架、插件系统或假设中的扩展层。

仅当复用会导致长期 wrapper、patch、fork 或更高整体复杂度，或无法满足当前必要需求时，才重新实现。重新实现时只承担真正缺失的部分，底层成熟能力继续复用。

```text
外部已有实现
≠ 必须使用

自己可以实现
≠ 应该重新实现
```

判断标准仍是：最小化系统整体复杂度，而不是最大化第三方依赖数量或代码复用率。

不要求每次普通代码修改都搜索外部实现。仅在准备新增长期能力、具有明显通用性、存在合理概率已有成熟实现时，才进行有限调查；证据足够支持复用或重新实现的决定后即停止。

---

## 持续设计

不要默认把新行为继续追加到已有文件、类或模块。

在实现非 trivial 改动前，应快速判断：

- 新行为属于哪个责任；
- 当前模块是否真正负责这个概念；
- 是否已有自然的结构边界；
- 当前变化是否暴露出新的概念、责任或变化轴；
- 是否需要先做局部结构调整。

设计应与实现一起演进。

早期 vertical slice 可以用于获得真实信息，但当新信息证明原结构不再合适时，应允许重新划分模块、移动责任、修改内部接口并删除旧实现。

不要无限 patch，也不要在实现前进行不必要的大规模设计。

---

## 结构判断

模块边界应根据概念、责任和变化方向划分，而不是根据机械指标划分。

文件长度、函数数量和分支数量可以作为结构压力信号，但不能成为强制拆分规则。

当出现以下情况时，应重新检查结构：

- 一个模块处理多个独立业务概念；
- 新功能反复修改同一个中央文件；
- mode、type 或特殊分支持续增加；
- 同一业务规则散落在多个位置；
- 一个模块同时承担编排、业务规则、持久化和表现层责任；
- 新行为找不到自然归属，只能继续放入 `service`、`manager`、`utils` 或 `helpers`；
- 修改某个功能时容易影响明显无关的行为。

合理拆分应提高内聚、明确责任并局部化变化。

不要为了降低文件行数创建无意义的 wrapper、转发层或新的垃圾桶模块。

---

## 开发收敛

PR 是一次变化的收敛单元，不是开发过程中每个中间状态的兼容边界。

在没有形成真实外部依赖时，允许：

- 删除旧实现；
- 重写内部接口；
- 修改全部可控消费者；
- 重新划分模块；
- 整理或重写尚未发布的 migration；
- 删除临时 fallback；
- 替换错误抽象。

最终代码应表达当前有效设计，而不是保存开发过程中的每次尝试。

> Git 保存演化历史，当前代码表达当前设计。

一个变化可以认为已经收敛，当：

- 当前需求具有一致、完整的实现；
- 不再同时保留互相竞争的新旧设计；
- 临时兼容、fallback 和过渡路径已经清理；
- 当前结构能够自然表达实现后的系统；
- 已获得足够的最新验证证据；
- 不存在影响当前交付的 material gap。

收敛不意味着代码不能继续优化。

当进一步修改只属于可选改进，而不再是完成当前目标或修复明显结构问题所必需时，应停止当前变化。

---

## 兼容与迁移

兼容真实依赖，迁移真实状态，不兼容开发过程。

不要为从未形成真实依赖的中间实现保留：

- compatibility layer；
- legacy fallback；
- deprecated path；
- 多余版本判断；
- 临时格式转换；
- 开发过程产生的 migration chain。

只有会在当前变化后继续独立存在的旧消费者或旧状态，才可能形成兼容或迁移义务，例如：

- 已发布的 public API、SDK 或 CLI；
- 无法随当前变化同时更新的其他系统；
- 用户已有配置、文件和数据；
- 生产或共享环境中的持久化状态；
- 需要支持滚动部署或回滚的新旧版本。

判断是否需要兼容或迁移时，应先问：

> 是否存在无法在当前变化中一起更新、重建或安全删除的真实消费者或状态？

如果 producer、consumer 和相关状态都处于当前可控范围内，通常应直接一起修改并收敛到新设计，而不是永久保留旧内部接口。

进入 `main` 不会自动使所有内部实现成为永久兼容契约。

稳定性应附着于真实契约和真实状态，而不是代码的位置、年龄或 Git 历史。

---

## 检查时机

检查、测试、构建、扫描和 review 不是越早、越频繁越好。

执行检查前，应明确：

- 它要验证的风险或假设；
- 结果会影响什么下一步决定；
- 当前状态是否已经适合产生有效证据；
- 是否存在成本更低但证据充分的检查。

如果检查结果不会改变当前下一步，或者实现仍处于已知不完整状态，通常应先完成当前工作单元。

行动前检查主要用于：

- 防止高风险或不可逆操作；
- 验证会改变实现方向的关键假设；
- 获取否则无法安全行动的信息；
- 建立确有必要的 baseline。

实现中的检查应在有意义的工作单元完成后进行，并优先使用最小相关验证。

更广泛、更昂贵的检查应在变化收敛后，或影响范围和风险确实要求时执行。

不要因为流程上“最终要检查”，就机械地提前或重复执行检查。

---

## 测试与验证

测试应保护长期有意义的行为，而不是保护当前实现方式。

优先测试：

- 业务规则；
- 状态转换；
- 输入验证；
- 权限与安全行为；
- public API 和模块契约；
- 持久化不变量；
- 数据一致性；
- parser、protocol 和 serializer；
- 重要失败路径；
- 明确发生过或容易复发的回归。

不要仅仅因为文件发生变化就新增测试。

以下变化通常不自动要求新增测试：

- README、文案和注释；
- CSS 或纯视觉调整；
- 简单 glue code；
- 文件移动和重命名；
- 纯格式化；
- 未改变行为的机械重构；
- 私有实现细节；
- 临时原型。

测试应尽量断言稳定、可观察的结果，而不是内部函数调用次数、私有结构或当前实现路径。

测试和验证不是同一件事：

- 测试是长期保护行为的自动化资产；
- 验证是为当前改动获得最新证据。

每个重要改动都需要适当验证，但不是每个改动都值得新增永久测试。

优先采用能够证明当前结果的最小有效验证；只有风险和影响范围要求时才扩大验证。

---

## 临时工具

Agent 可以为当前任务使用临时脚本、查询、转换程序和 debug instrumentation。

但“本次任务用过”不等于“项目需要长期拥有”。

只有在以下情况中，才应将工具作为正式仓库能力提交：

- 存在真实、明确的重复使用需求；
- 工具表达项目需要长期维护的规则；
- 多个开发者、环境或 CI 需要使用；
- 手工操作容易产生重要错误或风险；
- 操作需要正式审查、审计或重复执行；
- 工具本身属于正式交付内容。

对于一次性、低风险且最终结果可以直接审查的操作，应优先使用临时工具，只提交最终产物和必要验证。

不要为一次性任务建设通用 CLI、配置系统、插件结构、测试框架或 CI 流程。

> 允许制造施工工具，但不要默认把施工工具修进建筑里。

---

## 自主性

常规、局部、可逆且符合当前系统方向的决策，应自主完成。

不要因命名、局部组织、普通数据结构、小型内部重构、私有接口调整或 targeted verification 等问题频繁请求确认。

不确定性本身不是停止推进的理由。

当多个局部方案都合理时，选择最简单、最符合现有结构且足够完成目标的方案，然后继续验证。

高影响、难以逆转、改变外部契约、持久化状态、安全边界、产品行为或任务范围的决定，应按照决策边界处理。

---

## 完成语义

任务只有在以下条件满足时才能标记为 `DONE`：

- 用户要求的结果已经实现；
- 相关验收条件已经满足；
- 没有已知的重要部分被故意留在未完成状态；
- 有足够的 fresh evidence 支持完成判断；
- 没有为了快速完成而留下明显结构问题；
- 不存在仍需清理的虚假兼容、临时 fallback 或开发残留。

已经实现但尚未验证时，应明确说明：

`已实现，但尚未完成验证`

不得将其描述为 `DONE`。

任务属于 `BLOCKED`，仅当继续产生有效进展必须依赖：

- 用户信息；
- 外部权限；
- 缺失访问能力；
- 无法安全自主决定的重要决策。

任务属于 `HANDOFF`，当工作按照明确约定停在一个阶段边界，但整体目标并未被宣称完成。

不得将部分实现、placeholder、TODO、mock、未验证的重要行为或明显临时结构描述为完成。

---

## 沟通

计划和进度沟通应与任务规模相匹配。

当简短方向说明后即可行动时，不要输出长篇计划。

优先汇报：

- 已完成的实际结果；
- 关键工程决策；
- 验证证据；
- material risk；
- blocker；
- 尚未完成或尚未验证的部分。

不要逐条叙述常规工具调用，也不要用大量过程描述掩盖实际进展不足。
