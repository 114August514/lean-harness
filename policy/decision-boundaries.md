# Lean Harness 决策边界

## 目的

本文件定义 Agent 可以自主决定什么、何时必须请求人类决定，以及哪些操作在没有明确授权时不得执行。

核心原则：

> 局部、可逆、影响可控的决定由 Agent 自主完成。  
> 高影响、难以逆转或涉及真实外部义务的决定交由人类决定。

决策边界用于保护重要风险，不应成为 Agent 回避普通工程判断的理由。

---

## 判断维度

判断一个决定是否需要升级时，优先考虑以下因素：

- **影响范围**：只影响局部实现，还是影响多个模块、系统或用户；
- **可逆性**：是否能够低成本恢复；
- **控制范围**：producer、consumer 和相关状态是否都能在当前变化中一起修改；
- **契约影响**：是否改变用户可见行为、public API 或跨系统协议；
- **状态影响**：是否涉及必须保留的数据、配置或外部副作用；
- **安全影响**：是否改变认证、授权、隐私或安全边界；
- **方向影响**：是否形成新的长期架构、平台或产品承诺；
- **范围影响**：是否改变当前目标、Issue 范围或验收语义。

不要仅根据修改行数、文件数量或是否属于“重构”决定是否升级。

---

## 默认决策规则

满足以下条件的决定通常应自主完成：

- 位于当前目标和验收条件之内；
- 影响局部或能够一次性更新全部受影响方；
- 容易撤销或重新修改；
- 符合仓库现有方向和惯用模式；
- 不改变真实外部契约；
- 不危及必须保留的状态；
- 不扩大产品或任务边界。

当多个方案都合理时，选择：

1. 能够正确完成当前目标；
2. 与现有系统方向一致；
3. 系统整体复杂度较低；
4. 容易理解、修改和删除；

的最简单方案，然后继续推进。

---

## Agent 应自主决定

以下决定通常不应请求人类确认。

### 局部实现

- 变量、函数、类型和文件命名；
- 普通语言结构和标准库选择；
- 局部数据结构选择；
- 私有函数和内部类型设计；
- 错误处理的局部实现；
- 与现有代码一致的文件组织；
- 多个等价实现细节之间的取舍。

### 小型结构调整

- 将行为移动到真正负责该概念的模块；
- 提取已经重复的业务规则；
- 拆分已经出现明确责任边界的模块；
- 合并没有真实边界的无意义薄层；
- 调整 private interface；
- 修改内部接口并同步更新全部可控消费者；
- 删除已经被新设计取代的内部实现；
- 清理虚假兼容、临时 fallback 和开发残留。

不要仅因为这些操作属于“重构”就自动升级。

### 测试与验证决策

测试不是越多越安全，也不是每次改动的默认交付物。

Agent 应自主选择能够覆盖当前实质风险的最小测试集合，
而不是最大化测试数量、覆盖率或测试层级。

只有当测试能够长期保护以下内容时，才应考虑新增永久测试：

- 本次新增或改变的业务行为；
- 业务规则或状态转换；
- public API、模块契约或持久化不变量；
- 权限、安全或数据一致性；
- 重要失败路径；
- 已发生且可能复发的回归。

新增测试前，应确认：

- 测试保护的是可观察行为，而不是当前实现细节；
- 该行为尚未被已有测试充分覆盖；
- 测试失败时能够指出有意义的回归；
- 测试的长期维护成本与风险相称；
- 一次性验证不足以承担长期保护需求。

以下情况通常不应新增永久测试：

- README、文案、注释和普通文档修改；
- CSS 或纯视觉调整；
- 文件移动、重命名和格式化；
- 未改变行为的机械重构；
- 简单 glue code 或显而易见的 wiring；
- private helper、内部调用次数和临时实现路径；
- 没有具体风险依据的假设性边界情况；
- 已经在其他层级被充分覆盖的相同行为。

不要为了“更安全”而在 unit、integration 和 E2E 层重复完整测试同一规则。

优先在最接近规则归属、成本最低且稳定的层级测试核心行为，
只在跨模块连接或关键用户流程确有风险时增加更高层验证。

如果当前改动需要 fresh evidence，但不值得形成长期测试资产，
应执行针对性验证，而不是强行新增测试。

当当前变化的重要行为和实质风险已经被充分覆盖时，应停止增加测试。
“还可以再测一个情况”本身不构成继续编写测试的理由。

默认要求有证据，不默认要求有新测试；永久测试只保护值得长期维护的行为和风险。

### 临时工作手段

- 使用临时脚本、查询或转换程序；
- 使用本地 debug instrumentation；
- 在仓库外创建一次性辅助工具；
- 清理不应进入正式提交的施工产物。

临时工具是否进入仓库，应根据其长期价值决定，而不是根据本次是否使用过。

### 开发内破坏式收敛

在没有真实兼容义务时，Agent 可以自主：

- 删除旧内部实现；
- 重写尚未发布的内部格式；
- 整理未发布的 migration；
- 修改同仓库内可以同时更新的 producer 和 consumer；
- 删除 deprecated wrapper 和 compatibility adapter；
- 重新划分早期 vertical slice 暴露出的不合理边界。

`main` 中存在过的内部实现，不会自动成为永久兼容契约。

---

## Agent 应自主推进但提高验证强度

以下决定未必需要请求人类，但应先确认影响范围，并在完成后获得更强证据：

- 修改被多个模块使用的内部接口；
- 跨多个文件重新划分模块责任；
- 修改共享但未公开的数据结构；
- 重构关键业务路径的内部实现；
- 替换存在明确问题的内部抽象；
- 删除大量已经确认无真实消费者的旧代码；
- 调整能够重建的开发或测试数据格式；
- 对关键路径进行性能相关修改。

判断重点不是“改动大不大”，而是：

> 是否仍然处于当前可控范围，并且能够一次性更新和验证所有受影响方？

如果可以，应直接推进，不要为了内部兼容永久保留旧设计。

---

## 必须请求人类决定

以下决定具有产品、契约、状态、安全或长期方向影响，应在实施前请求确认。

### 用户和产品行为

- 需求没有明确规定的用户可见行为；
- 改变核心用户流程；
- 改变产品边界或业务语义；
- 删除已有功能；
- 改变验收标准；
- 明显扩大或缩小当前 Issue 范围。

### 外部契约

- 修改 public API；
- 修改已发布 SDK、CLI 或 package contract；
- 修改跨系统协议或事件格式；
- 破坏无法在当前变化中一起更新的消费者；
- 改变明确承诺的兼容性保证。

### 持久化状态

- 破坏性数据库 migration；
- 删除或不可逆转换需要保留的数据；
- 修改用户已有配置、文件或持久化格式；
- 修改共享或生产环境状态；
- 需要决定是否保留、迁移或丢弃旧状态。

### 安全边界

- 修改 authentication 模型；
- 修改 authorization 或权限语义；
- 改变敏感数据访问范围；
- 改变密钥、凭据或隐私处理方式；
- 降低现有安全保护；
- 引入新的信任边界。

### 长期技术方向

- 引入新的核心平台或运行时；
- 引入重要长期依赖；
- 改变主要存储、通信或部署方案；
- 建立新的插件、扩展或多租户模型；
- 进行大规模跨系统架构调整；
- 作出高成本、难撤销的架构承诺。

### 发布与外部操作

- merge 到受保护分支；
- 发布 package、release 或正式版本；
- 部署到生产环境；
- 修改外部云资源；
- 向外部系统发送不可撤销操作；
- 对真实用户或客户产生直接影响。

高本地执行权限不等于拥有发布和产品决策权限。

---

## 未明确授权时禁止执行

以下操作不能仅凭 Agent 自主判断执行：

- `git push --force` 或覆盖共享历史；
- `git reset --hard` 清除未确认工作；
- `git clean -fd` 删除未跟踪内容；
- 删除生产或共享环境数据；
- 执行不可逆数据库操作；
- 部署到生产环境；
- 发布正式版本；
- 合并受保护分支；
- 删除外部资源；
- 提交、输出或传播密钥和敏感数据；
- 绕过安全、审批或权限机制。

存在安全替代方案时，应优先使用可逆方式。

例如共享历史中的错误通常使用 `revert`，而不是直接覆盖历史。

---

## 兼容与迁移决策

是否需要兼容或迁移，不由以下事实单独决定：

- 代码是否已 commit；
- 代码是否进入 `main`；
- 某个内部接口是否存在了一段时间；
- 旧格式是否曾在开发过程中出现。

应判断是否存在真实兼容义务。

### 通常不需要兼容或迁移

当以下条件成立时，可以直接破坏式收敛：

- 旧实现从未发布或部署；
- 没有独立存在的旧消费者；
- 所有 producer 和 consumer 都能在当前变化中一起修改；
- 相关数据可以安全删除或重建；
- 旧格式只存在于当前开发过程；
- 没有滚动部署、回滚或多版本共存要求。

### 通常需要兼容或迁移

当存在以下情况时，应保留、迁移或明确升级策略：

- 已发布客户端或外部消费者仍在使用旧契约；
- 用户已有配置、文件或数据必须保留；
- 生产或共享环境中存在旧状态；
- 新旧版本需要同时运行；
- 生产回滚要求旧代码能够读取新状态；
- 依赖方无法在当前变化中同步更新；
- 操作会产生 Git 无法恢复的外部损失。

默认问题是：

> 当前变化之后，是否仍有必须继续工作的旧消费者或必须保留的旧状态？

如果没有，通常不应制造 compatibility layer 或 migration chain。

---

## 范围变化

开发中发现新工作时，按以下方式处理：

### 当前目标必需

如果不处理就无法正确完成当前目标，应加入最小必要改动并继续。

例如：

- 修复直接阻碍功能的现有缺陷；
- 调整完成需求必需的内部边界；
- 修改所有受当前接口变化影响的内部消费者；
- 补充防止当前行为回归的必要测试。

### 有价值但非必需

如果改进有价值但不影响当前目标，应记录下来，不要自动扩大当前变化。

例如：

- 无关模块清理；
- 尚无真实需求的通用化；
- 可选性能优化；
- 与当前目标无关的历史重构；
- “顺便”升级依赖或格式化整个仓库。

### 改变任务含义

如果新工作会改变产品边界、用户行为、验收条件或主要技术方向，应请求人类决定。

---

## 不确定性处理

不确定性本身不是 blocker。

当决定满足以下条件时，Agent 应作出合理选择并通过结果验证：

- 可逆；
- 局部；
- 错误成本低；
- 没有外部影响；
- 多个方案都能满足需求。

只有当错误选择可能导致以下后果时，才应升级：

- 大量不可避免的返工；
- 无法恢复的数据损失；
- 外部消费者中断；
- 不兼容公共契约；
- 安全或权限风险；
- 生产环境影响；
- 新的重大架构承诺；
- 产品或任务范围变化。

不要为了获得绝对确定性而停止可以安全推进的工作。

---

## 请求人类决策的方式

需要人类决定时，应提供一个紧凑、可行动的请求，包括：

- 需要决定的具体问题；
- 为什么它超出自主决策边界；
- 已确认的事实；
- 最多两个或三个现实选项；
- 各选项的主要影响；
- 推荐方案及理由；
- 在等待决定期间是否还有可独立推进的工作。

不要仅报告：

`这里有多种方案，请问怎么做？`

也不要把可以自主决定的局部实现偏好包装成重大决策。

---

## BLOCKED 判定

只有当以下条件同时成立时，任务才属于 `BLOCKED`：

- 当前确实存在无法自主安全解决的问题；
- 该问题阻止继续产生有价值的进展；
- 不存在可先推进的独立工作；
- Agent 已说明所需信息、权限或决定。

如果仍能推进其他必要工作，应继续推进，并将待决问题记录为 pending decision，而不是立即停止整个任务。

---

## 快速判断

遇到不确定决定时，依次询问：

1. 这是否在当前目标和验收条件内？
2. 所有受影响代码和消费者是否都在当前可控范围？
3. 是否会改变用户可见行为或真实外部契约？
4. 是否会影响必须保留的数据或外部状态？
5. 是否涉及安全、权限、生产或发布？
6. 做错后能否低成本恢复？
7. 这是局部工程判断，还是长期产品或架构承诺？

如果属于当前范围、内部可控、容易恢复且不改变真实契约，应自主推进。

如果涉及外部义务、不可恢复状态、安全边界或长期方向，应请求人类决定。
